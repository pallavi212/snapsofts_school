# EduSync — Database Keys, Codes & Foreign Key Guide

> How every ID, code, and foreign key works in this system.

---

## The Golden Rule

**Every person in the system is first a `users` row.**
Students, Teachers, Parents, Admins — all have a `users.id` (numeric) and a `users.user_code` (human-readable like `USR001`).
The role-specific tables (`students`, `teachers`) then link back to `users` via a foreign key on `user_id`.

---

## Code Types — What They Are & How They're Generated

| Code | Format | Example | Table | Generated By |
|------|--------|---------|-------|-------------|
| `user_code` | `USR` + 3-digit number | `USR001` | `users` | `MAX(id) + 1` on every insert |
| `student_code` | `STU` + 3-digit number | `STU007` | `students` | `MAX(id) + 1` on student create |
| `teacher_code` | `TCH` + 3-digit number | `TCH004` | `teachers` | `MAX(id) + 1` on teacher create |
| `receipt_no` | `RCP` + year + number | `RCP2025001` | `fee_payments` | Timestamp-based on frontend |
| `expense_no` | `PCE` + year + number | `PCE2025001` | `petty_cash_expenses` | `MAX(id) + 1` in PettyCashModel |

> **Important:** Codes are for display only. All foreign keys use the numeric `id` column, never the code string.

## Table-by-Table Foreign Key Map

### `users` — The root table
```
users.id  ←  referenced by almost every other table
users.user_code  ←  used in API URLs for updates/deletes (human-readable)
```
No foreign keys pointing out. Everything points IN to `users`.

---

### `teachers`
```
teachers.id          ← PK (numeric, used in all FKs)
teachers.user_id     → users.id          (ON DELETE CASCADE)
teachers.teacher_code ← display code only, used in API: PUT /api/teachers/:teacher_code
```
**When you update a teacher:** the API receives `teacher_code` → model looks up `teachers.id` internally → updates both `teachers` and `users` rows in one transaction.

```js
// TeacherModel.update — uses teacher_code to find the row
UPDATE teachers t JOIN users u ON t.user_id = u.id
SET ...
WHERE t.teacher_code = ?   // ← human code used here
```

---

### `students`
```
students.id            ← PK (numeric, used in all FKs)
students.user_id       → users.id          (ON DELETE CASCADE)
students.class_id      → classes.id
students.parent_user_id → users.id         (the parent's login account)
students.student_code  ← display code only, used in API: PUT /api/students/:student_code
```
**When you update a student:** the API receives `student_code` → model finds the row → updates `users` + `students` + optionally `classes`.

```js
// StudentModel.update — uses student_code to find the row
UPDATE users u JOIN students s ON s.user_id = u.id
SET ...
WHERE s.student_code = ?   // ← human code used here
```

**Parent link:** `students.parent_user_id` stores the parent's `users.id` (NOT the `parents` table id). This is how the parent portal finds children:
```sql
SELECT * FROM students WHERE parent_user_id = ?  -- ? = logged-in parent's users.id
```

---

### `teacher_classes` — Junction table
```
teacher_classes.teacher_id → teachers.id   (ON DELETE CASCADE)
teacher_classes.class_id   → classes.id    (ON DELETE CASCADE)
```
No codes here — pure numeric IDs. When saving assigned classes for a teacher:
1. Delete all rows for that `teacher_id`
2. Look up `classes.id` by class name (e.g. "5A")
3. Insert new rows

```js
// TeacherModel._syncClasses
DELETE FROM teacher_classes WHERE teacher_id = ?   // numeric teachers.id
SELECT id FROM classes WHERE name IN (?)           // resolve "5A" → class_id
INSERT INTO teacher_classes (teacher_id, class_id) VALUES ?
```

---

### `attendance`
```
attendance.student_id → students.id   (ON DELETE CASCADE)
attendance.class_id   → classes.id
attendance.marked_by  → users.id
```
**The tricky part:** The frontend sends `student_code` (string) and class name (e.g. "1A"). The backend controller resolves them:
```js
// attendanceController.saveAttendance
// 1. Resolve class name → class_id
SELECT id FROM classes WHERE name = '1A'   // → class_id = 1

// 2. Resolve student_code → student_id
SELECT id FROM students WHERE student_code = 'STU001'  // → student_id = 4

// 3. Save with numeric IDs
INSERT INTO attendance (student_id, class_id, date, status) VALUES (4, 1, ...)
```

---

### `fee_payments`
```
fee_payments.student_id → students.id   (ON DELETE CASCADE)
```
The frontend uses `student_db_id` (which is `students.id`) — NOT `student_code`. This is fetched from `feeApi.getPayments()` which returns `s.id AS student_db_id`.

```js
// FeeModel.addPayment
INSERT INTO fee_payments (student_id, ...) VALUES (student_db_id, ...)
//                                                  ↑ this is students.id
```

---

### `timetable`
```
timetable.class_id   → classes.id
timetable.teacher_id → teachers.id
```
Both are numeric IDs. No codes used here.

---

### `calendar_events`
```
calendar_events.created_by → users.id
```

---

### `exams` + `results`
```
exams.class_id       → classes.id
results.exam_id      → exams.id      (ON DELETE CASCADE)
results.student_id   → students.id   (ON DELETE CASCADE)
```

---

### `school_notifications`
```
school_notifications.sent_by   → users.id
school_notifications.target_id → classes.id OR students.id (depends on target_type)
notification_reads.notification_id → school_notifications.id  (ON DELETE CASCADE)
notification_reads.user_id         → users.id                 (ON DELETE CASCADE)
```

---

### `petty_cash_fund`
```
petty_cash_fund.added_by → users.id
```

### `petty_cash_expenses`
```
petty_cash_expenses.approved_by → users.id
petty_cash_expenses.recorded_by → users.id
```

## Full Relationship Diagram (text)

```
users (id, user_code, role)
  │
  ├── teachers (user_id → users.id)
  │     └── teacher_classes (teacher_id → teachers.id)
  │                          (class_id  → classes.id)
  │
  ├── students (user_id → users.id)
  │     ├── parent_user_id → users.id  [parent's login]
  │     ├── class_id       → classes.id
  │     ├── attendance (student_id → students.id)
  │     ├── fee_payments (student_id → students.id)
  │     └── results (student_id → students.id)
  │
  ├── calendar_events (created_by → users.id)
  ├── school_notifications (sent_by → users.id)
  ├── notification_reads (user_id → users.id)
  ├── petty_cash_fund (added_by → users.id)
  └── petty_cash_expenses (recorded_by, approved_by → users.id)

classes (id, name like "5A")
  ├── students (class_id → classes.id)
  ├── teacher_classes (class_id → classes.id)
  ├── attendance (class_id → classes.id)
  ├── timetable (class_id → classes.id)
  └── exams (class_id → classes.id)
```

## How API Routes Use Codes vs IDs

| Operation | URL uses | Model resolves to |
|-----------|----------|-------------------|
| Update teacher | `PUT /api/teachers/:teacher_code` | `teacher_code` → `teachers.id` |
| Update student | `PUT /api/students/:student_code` | `student_code` → `students.id` via JOIN |
| Delete user | `DELETE /api/users/:user_code` | `user_code` → `users.id` |
| Add fee payment | `POST /api/fees/payments` body: `student_db_id` | `students.id` directly |
| Get student payments | `GET /api/fees/payments/:studentId` | `students.id` directly |
| Get parent's children | `GET /api/students/by-parent/:userId` | `users.id` of parent |
| Save attendance | `POST /api/attendance` body: `class` name + `student_code` | resolved to numeric IDs in controller |

---

## Why Two IDs? (user_code vs users.id)

- `users.id` — numeric auto-increment, used in all SQL JOINs and foreign keys. Fast, reliable.
- `user_code` (USR001) — human-readable, shown in the UI, used in API URLs so they're readable.
- `student_code` (STU001) — shown on fee receipts, attendance sheets, report cards.
- `teacher_code` (TCH001) — shown on timetables, class assignments.

**Rule of thumb:**
- SQL JOINs → always use numeric `id`
- API URLs → use human code (e.g. `/api/students/STU001`)
- Frontend display → show human code
- Foreign keys in DB → always numeric `id`
